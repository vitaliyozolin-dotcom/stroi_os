# Проверка модульных контрактов

Команды работают через финансовый или типизированный контекстный репозиторий.
Хранилище остаётся прежним: один локальный черновик, кеш восстановления и
серверный проект с ожидаемой ревизией. Подтверждение staging не выдаётся за saved.

`module-contexts.test.ts` проверяет каждый из семи новых адаптеров:

- Узкая модель чтения без общего проекта, журнала и финансов.
- Применение только принадлежащих модулю полей, включая защиту цены/ID проекта.
- Сохранение параллельных финансовых изменений и актуального аудита.
- Отказ после изменения прочитанных данных или переключения проекта.
- Защита повторного добавления связанного документа.

Интеграционные сценарии связывают снабжение с финансовой приёмкой и оплатой,
задачи и качество — с приёмкой этапа. Нельзя принять этап, пока открыты задачи или
контрольные точки. Фотографии должны относиться к текущему проекту/точке; отмена,
чужой файл и поздний ответ не регистрируются. Принятые доказательства защищены.

Проверки архитектуры запрещают бизнес-командам зависеть от AppState, StateChange,
React и адаптеров. Чистые construction-политики не импортируют sites, сеть или БД.
Совместимые серверные экспорты возвращают те же функции, что доменный public API.
Состав Docker/Sites закреплён тестами; артефакты дополнительно проверяются импортом.

Существующие characterization-тесты сохранили проверки результирующего проекта.
`tests/support/module-project.ts` подключает реальные production-сценарии и адаптеры
и раскрывает им результат локальной записи только для прежних утверждений тестов.
Бизнес-обёртки целого проекта для этого не возвращены в production-код.

Авторизация, ролевые проекции, платёжный журнал и CAS Telegram продолжают проверяться
прежними серверными тестами. `finance-repository.test.ts` и тесты общего workflow
проверяют offline-повтор, expectedRevision, объединение независимых правок и
остановку на конфликте. Запуск PostgreSQL auth lifecycle требует отдельной тестовой
БД; отсутствие этой БД отмечается явным skip, а не успешной проверкой.

## Worker и Telegram — 21.10.2026

Worker сокращён с 1783 до 347 строк и связывает модули вместо выполнения SQL
и обработки бизнес-команд Telegram. Совместимые экспорты сохранены.

- `telegram/write-actions.js`: подтверждения задач, заметок, расходов и файлов,
  смена статуса задачи; повторные проверки прав внутри CAS-записи, lease и аудит.
- `telegram/update-handler.js`: команды, сообщения, callback, выбор проекта,
  получение/освобождение lease черновика и классификация ошибок для webhook retry.
- `telegram/registration.js`: персональная привязка и восстановление проекции пользователя.
- `telegram/files.js`: ограниченная потоковая загрузка, ключ по проекту/черновику
  и восстановление метаданных уже сохранённого файла.
- `telegram/visibility.js`: редактирование карточек, устойчивое подтверждение и фото.
- `runtime/initialization.js`: прежний SQL, readiness и повтор после ошибки подготовки.
- `projects/snapshot.js`: прежнее чтение снимка проекта.

Схема, версия 17, HTTP API, expectedRevision и набор разрешённых действий сохранены.
SQL при переносе сверён с предыдущим Worker без изменения выражений. Восстановлены
пропущенные зависимости списка команд, ограничения файла 20 МБ и форматирования
Telegram-текста. Поведенческие тесты вызывают эти ветки через новые модули.

Новые проверки покрывают повтор callback, отзыв доступа/смену ответственного,
запрет завершения прорабом, восстановление после сбоя доставки без повторной истории,
выбор проекта до записи, чужой чат черновика и неподключённую группу, ошибку БД
для webhook retry, лимит файла, освобождение upload admission после ошибки,
ограничение текста и повтор после сбоя подготовки без демо-данных.

Node 22.13.0: 502 теста прошли, PostgreSQL auth lifecycle пропущен без отдельной
тестовой БД; TypeScript прошёл. Vite и упаковка Sites проверены в изолированной
копии под `/tmp`, импорт упакованного Worker успешен. Обычный `dist/client`
принадлежит другому пользователю и недоступен для перезаписи (`EACCES`).
Docker-сборка прошла; внутри Alpine 500 тестов прошли, три пропущены: PostgreSQL
и две bash-проверки сброса входа. Обе bash-проверки прошли в полном локальном прогоне.
Импорт Worker в собранном контейнере без сети успешен. Боевые данные и внешние
интеграции при локальных проверках не изменялись.
